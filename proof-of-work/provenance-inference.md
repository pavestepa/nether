# Proof of work: совместный вывод контрактов и access provenance

**Статус:** эксперимент выполнен, код и тесты — в [provenance/](provenance/).
**Связь с проектом:** проверяет самую рискованную часть реализации
[NMM](../docs/core-memory-managment.md) (§7.3, §11, §20, §21.7) на минимальной
модели, не затрагивая основной компилятор.

## 1. Задача и гипотезы

Правило NMM «владение не отмывает R в W» должно сохраняться при возврате
значения, цепочках вызовов, рекурсии и передаче владения. Контракт функции
(кто потребляет аргумент, что и с какими правами возвращается) выводится из
тела и зависит от контрактов вызываемых, поэтому проверка loans невозможна
до стабилизации всех контрактов.

| ID | Гипотеза | Как проверяется |
| --- | --- | --- |
| H1 | Совместный вывод контрактов и происхождения прав завершается и даёт устойчивый результат | E3: повторный анализ с итоговыми контрактами ничего не меняет |
| H2 | Контракт результата (вид + origins + право доступа) достаточен, чтобы запретить повышение R→W через return, цепочки функций и передачу O | E1 (кейсы N03), E5 (абляции) |
| H3 | Те же правила не отклоняют допустимые программы из NMM | E1: положительные кейсы N01, N02, N04–N06, ветвления, циклы, рекурсия |
| H4 | Совместный fixed point необходим: однопроходный вывод в порядке исходника пропускает нарушения | E2, E3 |
| H5 | Результат не зависит от порядка функций и обхода | E3: случайные перестановки |
| H6 | Стоимость остаётся практичной: число анализов тел линейно по числу функций на цепочках зависимостей | E3, E4 |

Нулевая гипотеза: достаточно локального анализа каждой функции с
пессимистичными допущениями о вызовах (она опровергается, если H4 подтвердится
без ложных отказов на допустимом коде).

## 2. Что реализовано

Пакет [provenance/](provenance/) — самостоятельный Rust-крейт без зависимостей
(вне workspace компилятора). Конвейер повторяет архитектуру NMM §21:

```text
текст → syntax (lexer, parser) → mir (типы, CFG, временные значения)
      → analysis (поток по CFG, liveness, loans, производный контракт)
      → infer (worklist до неподвижной точки по графу вызовов)
```

### 2.1. Подмножество языка

`class` с полями (поле-класс — owning-слот), `fn` с `var`-параметрами, `let`/`var`,
присваивание и перепривязка, `x.f = e` / `x.f += e`, `new C(args)` (позиционно
по полям), вызовы, `if`/`else`, `while`, `return`, целочисленные выражения.
Non-Copy — любой class, Copy — `i32`. Методов, дженериков, замыканий, weak и
каналов нет (§7 — ограничения).

### 2.2. Модель анализа

* **Origin** — абстрактная цель: `Param(i)` или `Alloc(site)` (место создания).
* Состояние точки CFG для каждого non-Copy локала: вид (`Owner`, `Alias`,
  `ParamRoot(i)`, `Mixed`), множество origins, право доступа `W`/`R`, режим
  loan, родители (цепочка reborrow), признак `moved`.
* **Права:** `var x = new T` → W, `let x = new T` → R; `let b = a` → R-alias;
  `var b = a` требует W у `a`; значение из `let`/R-параметра никогда не даёт W.
* **Loans по liveness.** Доступ к `x` конфликтует с живым (по обратному
  анализу живости, включая back edges циклов) пересекающимся alias `y`, если `y`
  не является предком `x` в цепочке reborrow. Различаются `NMM_BORROW_CONFLICT`,
  `NMM_SUSPENDED_ACCESS` (доступ к приостановленному родителю) и
  `NMM_INVALIDATION` (передача O при живом view).
* **Owning-позиции** (аргумент `new`, запись в owning-поле, consuming-параметр
  вызываемого) требуют owner-token: root-владелец, свежий temporary или
  не-`var` параметр (тогда параметр получает `+O` в контракте). Alias — ошибка
  `NMM_NO_OWNER_TOKEN`; `var`-параметр — `NMM_VAR_CONSUME` (N09).
* **Контракт функции** (решётка, `contract.rs`):
  * по параметру: `var` (W/R), `consuming` (O);
  * по результату: вид `Bottom < None | Fresh | Borrowed | Transferred < Conflict`,
    множество параметров-origins, право доступа результата (`W` только если все
    origins — `var`-параметры; при слиянии путей — более слабое).
* **Слияние путей:** внутри одного тела owned и borrowed результаты не
  смешиваются (`NMM_RESULT_CONTRACT`, NMM §11.4). Между итерациями fixed point
  `Borrowed → Transferred` допускается как монотонное уточнение, когда
  consuming параметра выясняется позже.
* **Вызов:** результат получает origins аргументов по контракту и право
  `max(право контракта, права аргументов)`. Контракт `Bottom` (ещё неизвестен)
  даёт значение с пометкой «неизвестно», не вносящее вклада в результат.
* **Fixed point:** worklist; при изменении контракта в очередь возвращаются
  вызывающие. Диагностики берутся из последнего анализа каждой функции (он
  выполнен при итоговых контрактах вызываемых).
* **Наивный режим** (`--naive`, для сравнения): один проход в порядке исходника,
  непроанализированные и рекурсивные вызываемые считаются «пустым» контрактом.

## 3. Как запускать

```sh
cd proof-of-work/provenance
cargo test --release                       # 5 тестов гипотез E1–E5
cargo run --release --bin pow -- --experiments
cargo run --bin pow -- cases/neg_16_transitive_consume.nr           # вывод контрактов и диагностик
cargo run --bin pow -- cases/neg_16_transitive_consume.nr --naive   # однопроходный режим
```

Размеченные кейсы лежат в [provenance/cases/](provenance/cases/): первая строка
`// EXPECT: ok` или набор кодов, строки `// CONTRACT:` фиксируют ожидаемые
контракты, `// NAIVE:` — ожидание для однопроходного режима.

Практический вывод: схему «контракт = (ownership параметров, вид результата,
origins, право доступа) + worklist по графу вызовов + loans по liveness» можно
переносить в `compiler/core` как основу M0–M1. Нулевая гипотеза опровергнута:
локальный анализ с пессимистичными допущениями отклоняет либо слишком много
(теряет `Borrowed`-результаты), либо недостаточно (E2, E5).

## 6. Найденные проблемы при реализации

Эксперимент выявил два места, где наивная реализация нарушала бы H5 и которые
стоит учесть в основном компиляторе:

1. **Монотонность вклада.** Если ошибка (например, «использование после
   передачи») блокирует вклад в контракт (возврат значения, признак consuming),
   то контракт зависит от порядка обработки: ранняя итерация оставляет «след»,
   который не исчезает при слиянии. Вклад в контракт должен вычисляться
   независимо от найденных ошибок.
2. **Вид результата при возврате параметра** (`Borrowed` или `Transferred`)
   зависит от итогового признака consuming и поэтому определяется после
   обхода всего тела, а не в точке `return`.

Кроме того, при переопределении локала (в цикле) его прежнее значение нужно
исключать из набора живых aliases, иначе возникает ложный конфликт.

## 7. Ограничения и угрозы валидности

* **Нет независимого оракула soundness.** Проверяется, что реализация даёт
  ожидания, выведенные из NMM вручную, и свойства вывода (устойчивость, порядок);
  не доказывается, что все допущенные программы безопасны. Следующий шаг —
  динамический интерпретатор с трекингом loans или дифференциальное сравнение
  с кодогенерацией и проверка в Rust.
* **Модель упрощена:** нет методов, дженериков, указателей на функции,
  интерфейсов, замыканий, weak, каналов, async, readonly-view хранилищ, путей
  полей (поле считается тем же origin, что и оболочка), индексов массивов.
  Alias не может быть передан в owning-позицию вообще (консервативно).
* **Случайные программы** на 92% отклоняются (плотные функции с множеством
  потенциальных ошибок); это снижает мощность проверок на допустимом коде,
  но компенсируется короткими программами и размеченными кейсами.
* **Сложность в худшем случае** (глубокие графы вызовов с частыми изменениями
  контрактов) не измерена. Высота решётки конечна (число параметров, 3 вида
  результата, 2 права), поэтому завершение гарантировано, но оценка числа
  итераций — только эмпирическая.
* **Alloc-sites в цикле** считаются одним абстрактным объектом (как в NMM §3);
  это консервативно, но не проверялось на точность.
* Диагностика `NMM_VAR_CONSUME` введена как рабочее имя для N09: в NMM §24
  отдельного кода нет.

## 8. Следующие шаги

1. Динамический оракул: исполнение CFG с реальными счётчиками loans и
   проверка, что допущенные программы не нарушают инварианты.
2. Перенос в `compiler/core` выполнен частично (NMM §26.1): вывод consuming-параметров
   до неподвижной точки ([consume.rs](../compiler/core/src/check/consume.rs)), требование O для всех consuming entries и отказ alias с NMM_NO_OWNER_TOKEN, запрет R→W на привязках и параметрах, oracle в
   [nmm.rs](../compiler/core/tests/nmm.rs). Права доступа результата и origins уже были в
   `mir::returns`. MIR verifier и полный набор NMM-диагностик ещё не завершены.
   Актуальная базовая линия — [0.1](../docs/0.1/status.md); эксперимент не задаёт альтернативную модель.
3. Расширение: пути полей, методы, дженерики (специализация контрактов),
   указатели на функции (N29), замыкания (NMM §17).
4. Измерение худшего случая fixed point на крупных кодовых базах.
