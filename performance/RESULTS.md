# Производительность Nether и Rust

Эквивалентные программы лежат в [bench/](bench/): `*.nr` и написанный вручную `*.rs`.
Запуск: `./run.sh [повторов]`. Берётся минимальное время из серии, коды выхода программ
сравниваются (результат вычисления возвращается кодом выхода).

- Nether: `nether build --release --overflow-checks=off` (генерация Rust + rustc `-C opt-level=3`).
- Rust: `rustc -C opt-level=3`, арифметика через `wrapping_*`, чтобы совпадать с `overflow-checks=off`.
- Машина: Apple M3 Pro (arm64), rustc 1.86.0, 5 повторов, дата 2026-10-23.

| Бенчмарк | Rust, с | Nether, с | Nether / Rust | Что измеряет |
| --- | ---: | ---: | ---: | --- |
| array_sum | 0.159 | 0.158 | 0.99× | цикл с индексацией массива `{i32;8}` |
| class_alloc | 0.371 | 0.372 | 1.00× | 20 млн `new` класса + метод (Box в Rust) |
| lcg | 0.765 | 0.764 | 1.00× | 10⁹ итераций линейного конгруэнтного генератора |
| struct_step | 0.125 | 0.118 | 0.95× | 4·10⁸ вызовов функции с `var`-структурой |
| collatz | 0.233 | 0.409 | 1.75× | цепочки Коллатца, деление и остаток `u64` |
| fib | 0.276 | 0.523 | 1.89× | рекурсивные вызовы `fib(40)` |

## Выводы

- На циклах, структурах, массивах и классах Nether совпадает с Rust (0.95–1.00×).
- Отстаёт на **вызовах функций** (fib, 1.9×) и на **делении/остатке** (collatz, 1.75×).
- Причина видна в [сгенерированном коде](../docs/0.1/rust-backend.md): каждая функция возвращает
  `Result<T, Fault>`, значения лежат в `MaybeUninit`-слотах с raw-указателями, а управление
  задаётся диспетчером `loop { match pc }` (baseline lowering из `status.md`). LLVM убирает
  большую часть этого в простых циклах, но не полностью на рекурсии и на операциях с
  проверкой деления (`checked_rem` и ветка `Fault`).
- Цель «уровень Rust» подтверждена на 4 из 6 микробенчмарков и **не** подтверждена на двух.

## Ограничения измерения

- Микробенчмарки не покрывают строки, коллекции, дженерики, интерфейсы, потоки: в языке
  их пока нет.
- Проверки переполнения отключены. С ними (`--overflow-checks=on`, по умолчанию в debug)
  Nether будет медленнее Rust с `wrapping_*`; сравнение с Rust в режиме проверок не проводилось.
- `class_alloc` в Rust использует `black_box`, иначе LLVM удаляет выделение и время падает
  до 0.024 с; без него сравнение было бы нечестным.
- Один процессор и одна версия rustc; разброс между запусками не оценивался.
- Размер бинарников, время компиляции и использование памяти не измерялись.

## Следующие шаги

1. Убрать `Result`/`Fault` из функций, которые не могут паниковать (рекурсия `fib` без деления).
2. Заменить диспетчер `pc` на структурный lowering там, где CFG приводим.
3. Для `/` и `%` с константным ненулевым делителем не генерировать ветку `Fault`.
4. Повторить замеры и добавить бенчмарки по мере появления строк, коллекций и дженериков.
