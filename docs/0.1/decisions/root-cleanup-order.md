# Порядок cleanup при замене owned root

Статус: принят вариант 1 пользователем (ответ «1»).

## Неопределённость

`docs/main.md` §69 требует уничтожать owned roots scope «в обратном порядке
успешной инициализации». §93 требует немедленно завершать lifetime старого
значения при замене. Не определено, меняет ли замена позицию самого root
в порядке cleanup scope. Для transfers внутрь группы обновление порядка явно
задано; для повторной записи local root такого уточнения нет.

```nether
var a = new Resource(1)
let b = new Resource(2)
a = new Resource(3)
// выход из scope
```

Resource здесь обозначает тестовый class, destructor которого записывает свой
номер в журнал. В обоих вариантах Resource(1) уничтожается при замене `a`.
Различается дальнейший наблюдаемый порядок вызовов destructors.

## 1. Каждое новое owned значение обновляет позицию root (принято)

После успешной замены `a` становится последним инициализированным root.
Полный журнал: `[1, 3, 2]`. После consuming move и последующей повторной
инициализации действует то же правило. Запись поля не меняет позицию целого
aggregate root; порядок его полей остаётся порядком объявления по §69.

Это трактует правило §69 по времени начала текущего owned lifetime. Для branches
и loops lowering должен сохранять фактический порядок успешных инициализаций.
Достаточно ограниченного числом активных roots cleanup state: история замен
не накапливается, GC/ARC не требуется. Checker destructor dependencies должен
учитывать возможные порядки на разных путях.

## 2. Позиция принадлежит локальному binding

Замена и повторная инициализация сохраняют исходную позицию `a`.
Полный журнал: `[1, 2, 3]`. Moved/неинициализированные roots пропускаются;
повторное заполнение включает root на прежнем месте. Для locals текущего
синтаксиса это обратный порядок выполнения их declarations в scope.

Такой контракт упрощает cleanup ladders и анализ зависимостей destructors,
но требует явно уточнить в §69, что очередная инициализация существующего
binding не меняет порядок roots. Правило transfers в группы остаётся отдельным.

## Общие требования и проверки после выбора

- Нормальный выход, return/break/continue и panic используют один порядок.
- Move исключает старого владельца из cleanup; повторная инициализация
  восстанавливает его согласно выбранному варианту.
- Неуспешное создание RHS не считается успешной инициализацией destination.
- Проверки сравнивают журнал destructors и live allocations в HIR/MIR/native,
  включая условную замену, loops, move/reinitialize и panic.
- Решение не меняет уже принятые правила views, class identity или storage modes.

Реализация resource cleanup следует варианту 1; вариант 2 оставлен как отклонённая альтернатива.
