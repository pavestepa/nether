1. Не определено, как объект покидает контекст создания.
new привязывает объект к текущему контексту, присваивание не переносит ownership, однако в §57 функция возвращает new User(...).
fn make_user(): User {
    return new User()
}

let user = make_user()
Нужно определить, куда принадлежит этот User: контексту вызывающего кода, отдельному возвращаемому региону или региону функции с продлённым lifetime.

Нужно чтобы в таких случаях внутри явно выводилось move. Получается что в случаях где происходит явный move, должен происходить move. При этои move должен быть высчитан так что в конце передачи в какую то функцию или return, он мог быть move. Это может выделение сразу в подходящем регионе.

2. Смешаны владение контекстом и владение переменной.
Сначала сказано, что объектом владеет контекст, затем схема показывает user → owns, second → view. Это две разные возможные модели.
let mut first = new User()
let second = first
first = new User()
Что происходит с первым объектом? Продолжает ли second действовать? Есть ли вообще особая «владеющая переменная», если память принадлежит региону?
Что раскрыть: кто именно владеет объектом, что делает переприсваивание, влияет ли исчезновение последней ссылки на destruction. При владении регионом переменная может быть просто ссылкой, через которую доступны определённые capabilities.

3. Уникальный mut пока не имеет достаточно точных правил.
В документе есть mut у параметра функции, но изменяющий метод выглядит как обычный:
fn set_age(age: i32): void {
    this.age = age
}
Неясно, где обозначается изменяемый receiver и как вызывающий код узнаёт, что методу нужен уникальный доступ. values.push(4) создаёт тот же вопрос для Vec.
Кроме того, уникальность должна учитывать ссылки через поля и контейнеры:
let first = user
let second = user

update(mut first, second)
Если update читает second во время изменения first, операция должна иметь определённый результат проверки.
Что раскрыть: начало и конец capability, временное ограничение других aliases, изменяющие методы, повторные заимствования и доступ к отдельным полям. Также нужно решить, распространяется ли mut user на объекты, доступные через поля user.

5. Views на строки и элементы контейнеров требуют правил инвалидирования.
get_name(): str возвращает данные из String, но не описана связь lifetime результата с receiver:
let name = user.get_name()
user.set_name("another")
print(name)
Нужно определить, запрещено ли изменение, копируются ли данные или сохраняется старое хранилище.
Такой же вопрос возникает при получении доступа к элементу Vec и последующем push, способном переместить буфер.
Что раскрыть: зависимости lifetime результатов от аргументов, slices, доступ по индексу и операции, инвалидирующие views. Для let name = "Alex" также нужен фиксированный тип по умолчанию, если контекст отсутствует.

6. Region allocation не объясняет поведение долгоживущей памяти и ресурсов.
Если серверный cache постоянно заменяет объекты, что освобождает старые данные? Если они принадлежат ApplicationRegion, память может накапливаться до завершения приложения.
Для File есть отдельная проблема: уничтожение перед освобождением региона не гарантирует своевременное закрытие файла. Большой регион может жить часами.
Что раскрыть: удержание недоступных объектов, рост и переallocation контейнеров, возможность ограничить lifetime ресурса, порядок destructors, циклические ссылки и завершение при ошибках. Если выбор регионов является оптимизацией, он не должен произвольно менять наблюдаемый момент закрытия ресурса.

7. Правило «runtime polymorphism требует dyn» не согласовано с virtual.
fn speak(animal: Animal): str {
    return animal.speak()
}

speak(new Dog())
Вызывается Animal.speak или Dog.speak? Если второй — runtime dispatch доступен и без dyn, и сформулированное правило нужно уточнить. Если первый — нужно объяснить назначение virtual и способ динамического вызова через базовый класс.
Что раскрыть: преобразование derived → base, диспетчеризацию через base, значение обычного interface-типа и ограничения dyn. Для dyn над struct также нужно определить хранение: borrowed view или owned упаковка.
Дополнительно добавлю, что по сути Animal можно статически вывести если это Dog или Cat или просто Animal и заранее во время коспиляции создать функцию с нужной реализацией.

8. Тип функции не описывает важные свойства вызова.
(User) => void не показывает, нужен ли функции mut, сохраняет ли она аргумент и является ли async. Пока неясно, какие функции можно присваивать такому значению.
Предлагаю чтобы в типе функции нужно было писать (mut User) => User

9. Async и передача между потоками описаны преимущественно ограничениями.
Нужно определить, что возвращает вызов async fn ...: User: User, Task<User> или другой awaitable; когда начинается исполнение; где работает spawn; может ли задача менять поток.
Если две дочерние задачи получают один user, structured lifetime гарантирует, что родитель дождётся их завершения, но сам по себе не объясняет совместимость их mutable accesses.
Для channel недостаточно разрешить struct: struct может содержать User, str или контейнер с такими значениями. А transfer buffer должен учитывать все aliases передаваемой памяти.
Что раскрыть: отмену, ошибки дочерних задач, уничтожение async state, допустимые типы сообщений с рекурсивной проверкой полей, endpoints каналов и поведение передачи при закрытом канале.
Тут предлагаю тебе выбрать вариант при котором будет максимальная производительность и простой синтаксис с ощущением что это очень высокоуровневый язык программирования

10. Грамматика. Разделение выражений переносами строк, приоритет операторов, различение {} как блока и массива, пустой inline array.

Разделение выражений переносами строк: 
пусть будет через \n, \r в "" или ''.
пусть будет форматирование как в Rust, тобишь println("{}", value); но при этом будет поддержка js-like foo(`${value}`)
При этом println("{}", value); это уникальный синтаксис который имеет тип функции (String, ...To<String>) => void
Такие типы аргументов могут иметь такие функции как fmt итд

различение {} как блока и массива, пустой inline array:
