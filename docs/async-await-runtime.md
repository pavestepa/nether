# Nether Async Runtime — модель асинхронности (stackless, вывод MaySuspend)

**Редакция от 2026-10-23 · зафиксированное архитектурное решение**

Документ фиксирует выбор модели асинхронности Nether: **stackless-задачи
(конечные автоматы) в духе Tokio, с выводом эффекта приостановки компилятором
и без цветов функций в исходном коде**. Он дополняет
[core-memory-managment.md](core-memory-managment.md) (NMM) §17, §18 и §20 и не
противоречит им. В вопросах памяти приоритет у NMM.

Это спецификация целевого поведения, а не заявление о реализации. Исходный
синтаксис, помеченный как открытый (§9), не утверждён.

## 1. Решение и мотивация

Цель языка — производительность уровня Rust при «бесплатном» синтаксисе.
Рассматривались две модели:

| | A. Stackless (Tokio-like) | B. Stackful (Go-like) |
| --- | --- | --- |
| Стоимость задачи | Структура фиксированного размера | Отдельный стек + context switch |
| Синтаксис | Без цветов при выводе эффекта | Без цветов |
| NMM | Приостановки видны компилятору, loans через `await` проверяются статически | Views внутрь стека ломаются при росте/копировании стека; нет GC для их исправления |
| Отмена | Drop состояния = обычный cleanup | Требует инжекции unwinding |
| Rust backend | Прямое отображение на `Future` | Свой рантайм, asm, проблемы с TLS и unwind |

**Выбрана модель A.** Причины: потолок производительности как у Rust,
совместимость с NMM (§18.3, §15.5), прямое отображение на Rust-бэкенд,
самая низкая стоимость реализации. Недостаток модели A — раскраска функций —
снимается выводом эффекта `MaySuspend` вместо ключевых слов `async`.

Каналы с передачей O (NMM §18.1) и структурированная конкуренция входят в
модель; от выбора A/B они не зависят.

## 2. Нормативные свойства

1. **Нет цветов в исходнике.** Функция не объявляется `async`; приостановка
   — эффект, выводимый из тела и транзитивных вызовов (NMM §20.1–20.2).
2. **Stackless.** Каждая приостанавливаемая функция компилируется в конечный
   автомат с фиксированным размером состояния. Отдельных стеков нет.
3. **Приостановка только в видимых точках.** Точки suspension известны
   компилятору и входят в CFG как отдельные рёбра.
4. **Состояние задачи — owned aggregate.** Значения, нужные после
   приостановки, принадлежат состоянию задачи (NMM §18.3).
5. **Нет скрытых затрат.** Не допускаются неявные heap allocation на каждый
   вызов, Rc/Arc/RefCell состояния, неявный clone (NMM §23).
6. **Cleanup детерминирован.** Деструкторы синхронны; ожидание выражается
   явным `finish`/`close` (NMM §15.5).
7. **Изоляция.** Обмен между задачами в разных контекстах — через передачу O
   по каналу (NMM §18).

## 3. Эффект MaySuspend

Эффект выводится по тому же алгоритму fixed point, что и остальные effects
(NMM §21.7), и входит в публичный контракт функции.

- Базовые источники: ожидание завершения задачи, `recv`/`send` канала,
  асинхронный I/O, `sleep`/timer, явный `yield`.
- Функция `MaySuspend`, если она вызывает `MaySuspend` функцию на пути,
  не доказанно недостижимом (NMM §16.4).
- Функция без эффекта — обычная sync-функция без накладных расходов.
- Изменение вывода эффекта (появление/исчезновение `MaySuspend`) меняет
  контракт и требует перепроверки зависимых модулей (NMM §20.2).
  Версионируется вместе с `model_version`.

**Непрозрачные вызовы** (function pointer, closure, interface, generic):
callable contract включает бит `MaySuspend`. Если цель неизвестна,
берётся консервативное объединение; несовместимые ABI — отказ (NMM §20.2).
Вариант с двумя ABI (sync и suspending) допускается как оптимизация, если
выбор статический.

**Рекурсия** через приостановку требует явного разрешения (размер состояния
не может быть вычислен); без него — диагностика. Boxing допустим только как
явная библиотечная операция.

## 4. Представление и backend

- Приостанавливаемая функция → Rust `Future`-совместимый автомат (state enum
  + поля, живущие через точки suspension).
- Состояние, содержащее ссылки на себя, закрепляется (`Pin`) или лоуэрится
  без самоссылок; backend обязан доказать стабильность адресов
  (NMM §18.3). Raw pointer в future без этого не принимается.
- В первой реализации допускается Tokio как рантайм; его выбор — backend/
  library решение, и NMM не делегирует ему ownership (NMM §18.3).
- Размер состояния определяется набором значений, живущих через точки
  suspension; значения, чья жизнь заканчивается до suspension, в состояние
  не попадают.
- `Send`-подобные ограничения Rust не просачиваются в диагностику: Nether
  выражает их через transferability (NMM §18.2).

## 5. Задачи и структурированная конкуренция

- **Запуск задачи** явный: `spawn` (имя не утверждено, §9). Результат —
  handle, владеющий задачей.
- **Borrowed-задача** (запущена в области, захватывает R/W) не переживает
  область: выход из области ожидает её завершения или отменяет её. Это
  статически проверяется как loan (NMM §8.2, §17.5).
- **Detached-задача** получает необходимые O или Copy; внешние R/W/weak
  связи запрещены (`NMM_TRANSFER_DOMAIN`, `NMM_CLOSURE_ESCAPE`).
- Замыкание, передаваемое в `spawn`, подчиняется NMM §17.7.
- Handle задачи — non-Copy; его drop без явного ожидания либо отменяет, либо
  отсоединяет задачу. Выбор — один зафиксированный режим (открыто, §9);
  скрытого поведения «по ситуации» нет.

## 6. Взаимодействие с NMM

| Тема | Правило |
| --- | --- |
| Loan через suspension | Допустим только при доказанном lifetime и отсутствии конфликтующего доступа на всём интервале; одного OS thread для доказательства недостаточно (NMM §18.3) |
| Weak guard | Не переносится через suspension, если не доказано отсутствие мутации/уничтожения (NMM §14.4) |
| Owned значение после suspension | Принадлежит состоянию задачи |
| Cleanup состояния | Один раз, при завершении или отмене задачи |
| Owning-cycle | Задача, владеющая своим handle, и подобное — запрещены (NMM §13) |
| Каналы | Передача O; судьба payload при закрытии/timeout/cancel определена API (NMM §18.1) |

## 7. Отмена

- Отмена — это **drop состояния задачи** в точке suspension, где она
  находится. Исполнение не прерывается посреди sync-участка.
- Состояние очищается как обычный owned aggregate: initialized части ровно
  один раз, в порядке NMM §15.3; guards завершаются.
- Panic во время cleanup при отмене подчиняется NMM §15.5.
- Библиотечные операции документируют **cancel-safety**: что происходит с
  payload при отмене в момент `send`/`recv` (вернуть либо очистить, но не
  потерять/дублировать O).
- Деструктор не приостанавливается. Асинхронное закрытие — явный
  `finish`/`close`, вызываемый до drop.

## 8. Диагностика и приёмочные сценарии

Дополнительные категории к NMM §24 (имена предлагаемые):

| Категория | Причина |
| --- | --- |
| `ASYNC_RECURSION` | Рекурсия через suspension без разрешённой формы |
| `ASYNC_SUSPEND_IN_DESTRUCTOR` | Деструктор имеет эффект `MaySuspend` |
| `ASYNC_LOAN_ACROSS_SUSPEND` | Loan/guard пересекает suspension без доказательства |
| `ASYNC_EFFECT_MISMATCH` | Callable contract не соответствует выведенному `MaySuspend` |

Сценарии (продолжение матрицы NMM §25.3):

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| A01 | Функция без приостановок вызывается из sync-контекста | Pass, без накладных расходов автомата |
| A02 | Транзитивный вызов `MaySuspend` из sync-обработчика без моста | Compile-fail с указанием пути эффекта |
| A03 | R loan через suspension с доказанным lifetime | Pass |
| A04 | W loan через suspension при конфликтующем доступе из другой задачи | Compile-fail |
| A05 | Weak guard через suspension | Compile-fail, если не доказано |
| A06 | Отмена задачи между suspension | Cleanup состояния ровно один раз, O не потеряно и не продублировано |
| A07 | Borrowed-задача с выходом из области | Ожидание/отмена; нет использования после освобождения |
| A08 | `spawn` с внешним R/W capture | Compile-fail (`NMM_TRANSFER_DOMAIN`) |
| A09 | Function pointer / interface с неизвестным `MaySuspend` | Консервативный контракт либо отказ при несовместимых ABI |
| A10 | Рекурсия через suspension | Диагностика (`ASYNC_RECURSION`) |
| A11 | Суспендирующий деструктор | Compile-fail |
| A12 | Размер состояния: значение, умирающее до suspension | Не входит в состояние |

Проверяются на symbolic MIR до реализации source async (NMM §18.3).

## 9. Открытые детали

- Исходный синтаксис: нужен ли явный `await`/маркер точки ожидания, имя и
  форма `spawn`/`go`, синтаксис `yield`. Эффект при этом выводится в любом
  случае.
- Режим drop handle задачи: cancel или detach.
- Разрешённая форма async-рекурсии.
- Выбор рантайма (Tokio или собственный) и интерфейс планировщика.
- Конкретные сигнатуры каналов, `select` и timers.
- Поверхность callable типов с `MaySuspend` (связано с NMM §17.4).
- Политика двух ABI (sync/suspending) и специализация generics.

До принятия решений допускается явный unsupported diagnostic. Нарушение
нормативных свойств §2 не допускается ради реализации.

## 10. Порядок реализации

Расширяет синхронное ядро согласно NMM §27:

| Этап | Объём |
| --- | --- |
| S0 | Вывод `MaySuspend` в effects и контрактах; диагностика A02, A09, A11 |
| S1 | Автомат состояния, лоуэринг на Rust `Future`, проверка loans через suspension (A03–A05, A12) |
| S2 | Задачи, `spawn`, структурированные области, отмена (A06–A08) |
| S3 | Каналы с передачей O, cancel-safety API |
| S4 | Рекурсия, два ABI, собственный планировщик (при необходимости), замеры производительности против эквивалентного Rust |
